# ThanosRuleQueueIsDroppingAlerts

**PrometheusRule Source:** `cluster-monitoring-operator` · **Pending For:** `5m` · **Severity:** `Critical` · [Runbook](https://github.com/openshift/runbooks/blob/master/alerts/cluster-monitoring-operator/ThanosRuleQueueIsDroppingAlerts.md)

---

## Meaning

The ThanosRuleQueueIsDroppingAlerts alert triggers when the Thanos Ruler queue is found to be dropping alerting events.

The Thanos Ruler component is deployed only when user-defined monitoring is enabled. The component enables alerting rules to be deployed as part of user-defined monitoring. These rules can query the Prometheus instance responsible for core cluster components and also the Prometheus instance used for user-defined monitoring.

---

## Impact

* Alerts for user workloads might not be delivered.
* Alert notifications can be dropped while the Thanos Ruler queue is saturated.
* Important workload alerts may not reach Alertmanager and downstream notification systems.
* Excessive alert generation can reduce the reliability of monitoring for user workloads.
* Duplicate or incorrectly configured alerts can overload the Thanos Ruler alert notification queue.

---

## Diagnosis

Determine why Thanos Ruler is generating or receiving an unusually large number of alert notifications.

***1. Review the Thanos Ruler Logs***

Review the logs for the Thanos Ruler pods:

```bash
oc -n openshift-user-workload-monitoring logs -l 'thanos-ruler=user-workload'

level=warn ... msg="Alert notification queue full, dropping alerts" numDropped=100
level=warn ... msg="Alert batch larger than queue capacity, dropping alerts" numDropped=100
```
Thanos Ruler is dropping alerts because the alert notification queue has reached its capacity.

If the alert is firing, it is likely that the user-defined monitoring stack is generating an extremely large number of alerts.

---

***2. Review Active Alerts***

Log in to the OpenShift web console and navigate to:

**Observe → Alerting → Firing**

Review the active alerts and identify whether an unusually large number of alerts are firing.

* A large number of instances of the same alert.
* Duplicate alerts.
* Alerts generated from the same namespace or workload.
* Recently created or modified alerting rules.
* Alerts generated by a single `PrometheusRule`.
* Alert expressions that match a large number of time series.

---

***3. Identify High Alert Cardinality***

Use Prometheus to determine the number of firing alert instances:

```promql
count(ALERTS{alertstate="firing"})
```

Identify which alert names are generating the largest number of firing instances:

```promql
count by (alertname) (
  ALERTS{alertstate="firing"}
)
```

Identify the namespaces generating the largest number of firing alerts:

```promql
count by (namespace) (
  ALERTS{alertstate="firing"}
)
```

Identify the combination of namespace and alert name:

```promql
count by (namespace, alertname) (
  ALERTS{alertstate="firing"}
)
```
Use the queries to determine whether a specific alert or namespace is responsible for an unusually large number of alert instances.

---

***4. Identify the PrometheusRule Responsible for the Alerts***

Once an alert with unusually high cardinality has been identified, locate the corresponding `PrometheusRule`.

List PrometheusRules across the cluster:

```bash
oc get prometheusrules -A
```

Inspect the suspected PrometheusRule:

```bash
oc -n <namespace> get prometheusrule <prometheusrule-name> -o yaml
```

Review:

* `spec.groups[].name`
* `spec.groups[].interval`
* `spec.groups[].rules[].alert`
* `spec.groups[].rules[].expr`
* Alert labels
* Alert annotations

For example:

```yaml
rules:
- alert: ExampleAlert
  expr: some_metric > 0
```

If `some_metric` contains a large number of unique series, the expression can generate a correspondingly large number of alert instances.

---

***5. Check for Duplicate or Erroneous Alerts***

List all PrometheusRules:

```bash
oc get prometheusrules -A
```

Search for the alert name:

```bash
oc get prometheusrules -A -o yaml | grep -n "<alert-name>"
```

Determine whether the same alert is defined in multiple PrometheusRules.

Also check whether multiple rules are evaluating the same metric and generating duplicate or overlapping alert instances.

---

***6. Review Recently Created or Modified PrometheusRules***

Check for recently created PrometheusRules:

```bash
oc get prometheusrules -A --sort-by=.metadata.creationTimestamp
```

Inspect recently modified or suspected rules:

```bash
oc -n <namespace> get prometheusrule <prometheusrule-name> -o yaml
```

Review whether a recent change:

* Removed a metric filter.
* Increased the number of matching time series.
* Added a high-cardinality label.
* Changed the alert expression.
* Changed the rule evaluation interval.
* Created a duplicate alert.
* Caused a workload to generate significantly more metrics.

---

***7. Secondary Investigation — Thanos Ruler to Alertmanager Communication***

If the Thanos Ruler logs do **not** show queue-full or queue-capacity messages, investigate the communication path between Thanos Ruler and Alertmanager.

Check for:

* Network connectivity problems.
* NetworkPolicy restrictions.
* DNS resolution problems.
* Alertmanager availability.
* Connection timeouts or `context deadline exceeded` messages in Thanos Ruler logs.

Check the Thanos Ruler logs for communication-related errors:

```bash
oc -n openshift-user-workload-monitoring logs -l 'thanos-ruler=user-workload' | grep -Ei 'timeout|deadline|alertmanager|connection|connect'
```

Check Alertmanager pod status:

```bash
oc -n openshift-monitoring get pods -l app.kubernetes.io/name=alertmanager
```

If Alertmanager pods are unavailable or repeatedly restarting, investigate Alertmanager health separately.

---

## Mitigation

***1. Correct the Misconfigured/Duplicate/Errored/changed PrometheusRule***

The default queue capacity for Thanos Ruler is quite high at 10,000 items, which means that the most likely cause of this issue is a misconfiguration that causes the user-defined monitoring stack to overload Thanos Ruler with duplicate or otherwise erroneous alerts. 
Review all active alerts in the OpenShift web console and correct any misconfigurations.

```bash
oc -n <namespace> get prometheusrule <prometheusrule-name> -o yaml
```

***2. Temporarily Disable/remove the Problematic Alert Rule***

If a PrometheusRule is continuously generating an excessive number of alerts and the underlying configuration cannot be corrected immediately, temporarily disable the problematic alert according to the change-management process.


> Do not delete the complete PrometheusRule if it contains other valid alerting rules. Modify only the problematic rule whenever possible.

---

***3. Consider Alert Grouping***

Alert grouping can be used to reduce the number of individual notifications generated.

Review the Alertmanager grouping configuration and determine whether related alerts can be grouped using appropriate labels.

---

***4. Verify***

After correcting the problematic alert configuration, monitor the Thanos Ruler logs:

```bash
oc -n openshift-user-workload-monitoring logs -l 'thanos-ruler=user-workload' --since=10m
```

### Check the alert status:

**Observe → Alerting → Firing**

Verify that `ThanosRuleQueueIsDroppingAlerts` transitions out of the firing state after the underlying queue-drop condition has recovered.
